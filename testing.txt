2. HOW SEARCH WORKS - LIVE TESTS
================================================================================

Recall the flow (docs/phase5.md): the Search Service calls the search
black box first; the black box returns ranked {productId, score} pairs
(including, in this mock, one deliberately injected FAKE/invalid product
ID with the top score, to prove we never trust it blindly); we hydrate
those IDs against the real Product DB, filter out inactive/out-of-stock/
unknown products, apply business filters (sellerId, isActive) the black
box doesn't know about, optionally re-sort by price, and return the page.

--------------------------------------------------------------------------------
TEST S1 - Text search: GET /products/search?q=headphones
--------------------------------------------------------------------------------
Request:  GET /products/search?q=headphones

Response:
{
  "results": [
    {
      "name": "Wireless Headphones",
      "price": 4999,
      "quantity": 15,
      "isActive": true
    }
  ],
  "page": 1,
  "limit": 20,
  "total": 1
}

Result: PASS - exact single match on name.

--------------------------------------------------------------------------------
TEST S2 - Text search: GET /products/search?q=code
--------------------------------------------------------------------------------
Matched: "Clean Code" only (total: 1).

Note: "The Pragmatic Programmer" was NOT matched - "code" doesn't appear
in its name or description. This shows the matching is real text search
against name/description, not a fuzzy "related topic" match (that kind of
semantic matching is explicitly out of scope - it's exactly the kind of
thing the real black box, not our code, would be responsible for).

--------------------------------------------------------------------------------

--------------------------------------------------------------------------------
Matched (total: 3), in black-box relevance order:
    Smart Watch            Rs 7999
    Bluetooth Speaker      Rs 2999
    Wireless Headphones    Rs 4999

Result: PASS - all 3 Electronics products returned, no Books/Shoes leaked in.

    Bluetooth Speaker    Rs 2999

3. HOW RECOMMENDATIONS WORK - LIVE TESTS
================================================================================

Recall the flow (docs/phase4.md): the Recommendation Service calls the
black box with {userId, limit}; the mock returns {productId, score} pairs
for a RANDOM sample of products (again, with one injected invalid product
ID at the top score) - this mock does NOT do real personalization, since
implementing actual ML/personalization logic is explicitly out of scope
for this project (see readme.txt's "WHAT NOT TO BUILD"). What IS real and
tested here: the integration contract, the hydration/filtering of
whatever the black box returns, and the fallback-to-trending behavior
when the black box is unavailable.

--------------------------------------------------------------------------------
TEST R1/R2/R3 - Personalized recommendations (black box UP)
--------------------------------------------------------------------------------
GET /recommendations?userId=<Alice>&limit=5
  source: "personalized"
  Clean Code, The Pragmatic Programmer, Bluetooth Speaker, Travel Backpack

GET /recommendations?userId=<Bob>&limit=5
  source: "personalized"
  Leather Wallet, Bluetooth Speaker, Smart Watch, Running Shoes

GET /recommendations?userId=<Test User>&limit=5
  source: "personalized"
  Clean Code, Comfortable Sandals, Smart Watch, The Pragmatic Programmer

Result: PASS, with an honest caveat: because the mock black box picks a
RANDOM sample rather than genuinely reasoning about each user's history,
these three lists are not meaningfully different from each other despite
Alice/Bob/Test User having very different purchase histories. This is
EXPECTED and correct given the project's explicit scope: "we do NOT
implement any ML model... Our application should NOT know how the
recommendation algorithm works" (readme.txt). What's actually being
verified here is the CONTRACT and plumbing: the call succeeds, returns
"source": "personalized", and every returned product is a real, active,
in-stock product - not whether the picks are smart.

The mock ALWAYS injects one hardcoded invalid productId
(00000000-0000-0000-0000-000000000000, score 0.99 - always the top
score) into every raw response it returns, by design (see
docs/phase4.md). Across all three final API responses (R1/R2/R3) above,
that invalid ID never appeared - confirmed filtered out by hydration
every time, despite always being the highest-scored "pick."

Note on reproducing this exactly: the mock recommendation engine picks
its candidate sample via `ORDER BY random()`, so every call returns a
different random set - the raw example below is a separately captured
call (not the literal input to R1/R2/R3 above), shown purely to
illustrate what hydration/filtering strips out before a response ever
reaches the client:

  Raw black box response (POST /recommendation-engine/recommend, one
  independent sample call, 6 candidates unfiltered):
    00000000-... (score 0.99) <- fake/invalid, injected by the mock
    07c9b72d-... Clean Code                   (score 1.0)
    0841ce85-... Running Shoes [OUT OF STOCK] (score 0.95)
    43800295-... Comfortable Sandals          (score 0.9)
    ae7d90a1-... Leather Wallet               (score 0.85)
    577175c3-... Smart Watch                  (score 0.8)

  If this exact candidate set were hydrated, the invalid ID and the
  out-of-stock "Running Shoes" would both be dropped, leaving: Clean
  Code, Comfortable Sandals, Leather Wallet, Smart Watch - 4 usable
  products out of 6 raw candidates. The three REAL API responses in
  R1/R2/R3 above each went through this identical hydration/filtering
  step against their own (different) random samples, which is why
  their invalid-ID/out-of-stock counts vary per call.

--------------------------------------------------------------------------------
TEST R4 - Recommendation black box DOWN (fallback to trending)
--------------------------------------------------------------------------------
Action: killed the mock recommendation-engine process entirely.
Request: GET /recommendations?userId=<Alice>&limit=5

Response: source: "fallback"
    Running Shoes, Travel Backpack, Comfortable Sandals,
    The Pragmatic Programmer, Leather Wallet

Result: PASS - this is a dramatically more honest list than the
"personalized" ones above, and it's driven entirely by real data: the
top two (Running Shoes, Travel Backpack) are EXACTLY the two products
with purchase counts above 1 (7 and 2 respectively, from the purchase
count table in section 1) - the trending-by-purchase-count fallback
query (docs/phase4.md) is working correctly, not just returning random
or newest products.

--------------------------------------------------------------------------------
TEST R5 - Recommendation black box restarted (and the Redis cache catch)
--------------------------------------------------------------------------------
Action: restarted the mock, immediately re-ran the same request for Alice.

First attempt: source still came back "fallback" - NOT a bug. The
recommendation result from Test R4 had already been cached in Redis for
300 seconds (docs/phase6.md), keyed by userId+limit, and this request hit
that cache - so it correctly returned the exact same cached response
rather than making a new black-box call.

After manually clearing that one cache key (redis-cli DEL
"recommendations:<Alice>:5") and re-requesting: source: "personalized" -
confirming the black box was genuinely back up and the caching layer
behaves exactly as designed (cache-aside, 5-minute TTL, doesn't magically
know the black box recovered mid-TTL-window).
